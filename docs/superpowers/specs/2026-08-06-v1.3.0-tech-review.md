## 1. ask_gate 接入点 —— ✅ 可行

**实证**：
- `src-tauri/src/scheduler.rs:1170`：消息 ingestion 路径检测 @mention（A2A）→ 写 `mentions` 表
- `src-tauri/src/db.rs:1450`：`INSERT INTO task_runs(...,status,created_at,phase,phase_updated_at) VALUES(...,'queued',...` —— task_runs 创建唯一入口在此
- 跨群 A2A 走 `src-tauri/src/a2a.rs` / `web.rs` 独立模块

**结论**：Ask 过滤 hook 插在 scheduler.rs 的「mention 解析完成 → db.rs:1450 创建 run」之间。白名单外消息**不调用创建函数**，落入待办队列（新表或 run_events 扩展）。
**风险**：实现时需确认 a2a.rs 的跨群消息是否复用同一 ingestion 函数（若复用，白名单必须包含 A2A 来源标记，否则误伤）。

## 2. 表结构兼容 —— ✅ 可行

**实证**（`src-tauri/src/db.rs`）：
- 旧表独立存在：`roadmap_items`(:85) / `features`(:91) / `feature_tasks`(:100) / `roadmap_orchestrations`(:187)，与拟新增的 `project_versions` / `version_roadmaps` / `waves` 无命名冲突
- `task_runs` 已含 `phase` / `phase_updated_at`（:154-155 ALTER 追加），且 :122 有通用 `ALTER TABLE task_runs ADD COLUMN` 工具 → 追加 `version_id` / `wave_id` 列成本极低
- 生产数据量：本机 `data/*.db` 均为 0 字节占位（真实 DB 路径由运行时 `open_db(path)` 传入），**无法离线核实**；SQLite 单表万行级无压力，S1 只读保留安全。实现时从运行实例确认一次即可。

## 3. git_inspect —— ⚠️ 有条件可行（净新增）

**实证**：全仓 grep `git2` / `Command::new("git")` / `git log|tag` 于 `src-tauri/src/*.rs` **零命中** —— 平台 Rust 侧目前完全不读 git。

**方案**：
- 用 `Command::new("git")` 调系统 git（2GB 机器避免 git2 crate 编译与内存负担；`git log --oneline` 中型仓库约百 ms 级）
- 30s 缓存：Rust 侧进程内存 `Mutex<HashMap<repo_path, (Instant, Vec<TagInfo>)>>`，跨请求共享即可，无需落库
- 虚拟 Tag：无 tag 时按「首个 commit / 最近 commit 集群」生成，逻辑放 git_inspect 层（平台侧），Agent 只产 Roadmap 初稿/总结（对应产品审稿建议 5）

## 4. Wave 与 task_runs —— ✅ 可行（推荐复用 + 扩展）

**实证**：
- `task_runs` 现有 status 枚举：`queued / running / completed / failed / starting`（scheduler.rs 实证）——**无 paused/cancelled**
- 已有 `phase` 列可承载阶段 cursor

**方案**：
- 新增 `wave_runs` 表管 Wave 级状态（含阶段/细步 cursor）；执行载体**复用 `task_runs`**（加 `wave_id` 列），避免双轨调度
- ⏸ 语义落地：新增 status `paused`（仅 Wave 级）+ 当前 run 等其自然结束（不 kill）；▶ 从 `wave_runs.cursor` 续跑。与现有 queue 机制不冲突（⏸ 后不创建新 run 即可）
- **风险**：`paused` 是新枚举，需查前端/调度器对未知 status 的兜底（实现时加单测）

## 5. Codex loop —— ❌ 前提不成立

**实证**：
- `src-tauri/src/adapters/codex.rs:63-78`：`build_args` 是 **`codex exec` 单轮模式**（`--skip-git-repo-check` + deepseek provider 配置），全仓无 loop 模式实现（唯一 `loop` 命中在 `adapters/mod.rs:289`，是普通重试循环）
- 当晚实测（rollout 2026-08-06T01-54）：Codex turn 在打印命令后 **9.7s 即 task_complete、命令未执行** —— Codex 通道（deepseek 代理）当前**不可靠**

**结论**：S4 阶段 4「默认 codex loop」需**新增开发项**（多轮迭代直至测试通过/确认），且因通道不稳定，必须做 adapter 降级（fallback Cursor / OpenClaw adapter）。设计稿 §6 相应表述需修订（对应产品审稿建议 7 的补充）。
