# WorkPanel 小组件的形态判定与收敛路线（Widget Capability Placement）

> 配套：总设计 `2026-08-16-dsh-self-bootstrap-runtime.md`；群聊治理层 `2026-08-16-group-chat-governance-plane.md`；UI 设计语言 `2026-08-16-dsh-ui-language-workpanel.md`。
> 结论先行：**按 DSH 模式，「每个小组件单独建一个群」不宜继续。群聊是治理/协作平面，不是应用容器；小组件应下沉为「页签/能力」，只在「需要独立上下文 + 要人来议事拍板」时才有资格拥有一个群——而且那是一个项目群，不是一个 widget 群。**

## 问题 / 动机

WorkPanel 上陆续做了很多小组件（面板类、工具类、语音/视听类等；当前已有 `panellive` Extend，另有 DSH Web 嵌入）。历史上容易把每个组件对应一个群来组织。DSH 模式引入后，群聊被重构为「意图/决策层」（`group-chat-governance-plane.md`），每个群会自动预制不可改的 `bootstrap-dsh`、带默认响应者、关联决策卡/审批——这些都是**治理设施**，不是**运行容器**。

若给每个 widget 单独建群，会产生：

1. **层面错位**：把「执行平面的东西」错误提升到「治理平面」，大量群聊内容与「运行」有关而非与「决策」有关。
2. **治理噪音**：widget 越多群越臃肿，默认响应者/公告/审批关联随之泛滥。
3. **与 DSH 语义冲突**：DSH 的正确映射是 **widget = 能力（tool/skill/plugin）**，资格挂在 Agent/扩展宿主下随聊随用，而不是一组独立会话。会话在 DSH 里是可回放/可分叉的执行载体，不是「装一个工具」的容器。

## 两平面分清（映射到三层架构）

```text
治理/协作平面（WorkPanel 群聊 + 结构化层）
  ├─ 意图/决策层  群聊：为什么做、谁批准、审计叙事
  └─ 结构化状态层 版本/Wave · 决策卡 · diff · 会话重放
执行/能力平面（dsh / 扩展宿主）
  ├─ 页签/工具：被动工具、面板、视听 UI   ← 小组件的主场
  └─ 可注入能力：tool/skill/plugin（可回放、可回滚）
```

**结构性约束**：结构化存储是唯一事实源；群聊是围绕它的叙事入口。跨群共享的 widget 数据放结构化层，不放群聊。

## Widget 三分形态（判定矩阵）

| 形态 | 定义 | 适用 | 载体 | 是否建群 | 现有范本 |
|---|---|---|---|---|---|
| **A 被动工具/页签** | 人打开它去用的可视化组件（看板、OCR、翻译、语音、Live……） | 绝大多数 widget | 扩展页签：沿用 `/api/extensions/{id}/{*path}` 同源 iframe，或主视图页签 | ❌ 不建群 | `panellive`（Live）——**一个群内挂页签，没为它单独建群** |
| **B 能力注入 Agent** | 想被 Agent 干活时顺手调用的能力（检索、执行、查知识） | 面向 agent 调用的 widget | 声明为 dsh 的 tool/skill/插件；随聊随用，可回放、可回滚 | ❌ 不建群 | 轨道 G「能力 seam」（P2） |
| **C 治理型项目群** | 需要独立记忆/上下文 **且** 需要人机议事 + 审批的 widget | 极少数有「自我演进」诉求的组件 | 一个项目群：群聊讨论 → 决策卡 → bootstrap-dsh / `linlis-super-harness` 执行 → 灰度 → 审批 | ✅ 才建群 | 治理层「一次立项闭环」 |

> 注：C 形态的本质是「项目群」，不是「widget 群」——它依附于版本/Wave 与决策卡，执行走两级不可改自举 Agent，不豁免审批纪律（沿用 `2026-08-16-dsh-self-bootstrap-runtime.md` 护栏）。

## 「要不要建群」四问速查

1. **它需要和「人」对话议事事吗？** 不需要 → A/B，别建群。
2. **它需要独立上下文/工作区/记忆边界吗？** 不需要 → 别建群。
3. **它需要审批/治理吗？** 需要 → 不进「widget 群」，**并入某治理群/版本-Wave 流程**，决策落结构化层。
4. **它的价值是「被跑一遍」还是「被讨论后决定怎么改」？** 前者是能力，后者才是群聊。

## 落地形态（三栏 UI 对应）

| 三栏（`2026-08-16-dsh-ui-language-workpanel.md`） | widget 落点 |
|---|---|
| 左栏 导航 / 控制轨 | 「技能/扩展」入口：widget 注册列表、启停、健康 |
| 中栏 工作区（群聊） | 页签（形态 A）或工具行/回合尾动作（形态 B），即点即用 |
| 右栏 Agent（成员/子 Agent） | 每个 Agent 可用能力清单（形态 B 注入），执行中/排队、审批中心 |

规律：**widget 从「换一个群」变成「换一个页签/一件工具」**；群的增减只由「治理/协作边界」决定，不由「组件数量」决定。

## 收敛路线（现状 widget → 目标形态）

1. **盘点归类**：逐个 widget 过四问，标 A/B/C，不满足建群标准的先不建群。
2. **被动型 → 形态 A**：注册进扩展宿主（现有 `extensions` 机制，manifest + tab + 同源代理），从「每 widget 一群」迁到「一主群 + 多个页签」。
3. **能力型 → 形态 B**：等轨道 G P2「能力 seam / 可逆注册」落地后注入 dsh 工具/skill 名单，让群内 Agent 直接调用。
4. **治理型 → 形态 C（个别）**：才开群，且走「治理 → 干跑 → 灰度 → 审批」纪律，不豁免；权限写进群公告 + AGENTS。
5. **对既有「每 widget 一群」**：若该群没有独立记忆/议事诉求，收敛为「主群 + 页签」，必要时归档空壳群（保留历史消息）。

## 边界 / 不做

- **不把「单会话」当群聊替代**：WorkPanel 保持多群模型（沿用 `2026-08-16-dsh-ui-language-workpanel.md` 边界）。
- **不建「widget 目录群」做集中管理**：集中管理只在结构化层/左栏扩展入口做，不进群聊。
- **不因 widget 规模扩张群数**：群的增减只由治理/协作边界决定。
- 形态 B 依赖 P2 能力热载，在此之前能力型 widget 暂以形态 A 页签承载，不阻塞上线。

## 验收

- 一个新 widget 上线默认走「扩展页签（A）或工具注入（B）」，不新增群；新增群必须能说清「独立上下文」与「人机议事」两个理由。
- `panellive` 行为不变（页签即范本）；DSH Web 嵌入维持主视图内嵌，不另建群。
- 治理型群内自举改动仍必须附「可回放会话/干跑结果」才能进审批；无任何路径绕过 `manually_approved`。
- `docs/version-pipeline.md` 同步占位后，改动按「先占位再改码」纪律落地。
