# 群聊治理层：把群聊重构成「审议与管控台」

> 配套：总体规划 `2026-08-16-dsh-self-bootstrap-runtime.md`。
> 结论先行：自举能力越大，群聊越不可替代；但群聊必须从「聊天工具」升级为「议事 + 审批 + 叙事的管控层」，否则会叠加复杂度后被冲垮。

## 问题 / 为什么群聊仍然必要

引入 DSH 自举后，系统补上了「能造什么（执行层）」，但 DSH 天生缺「为什么做、谁批准、怎么不失控（决策/治理层）」。群聊承载的正是后者：

1. **人机合一的判断现场**：不是点抽象「同意」，而是在上下文里看动机/方案/风险后拍板。
2. **多 Agent 议事会**：架构 Agent 出方案 → 评审 Agent 质疑 → 执行 Agent 干跑 → QA Agent 把关，先辩论后动手。
3. **可解释的审计叙事**：一次自更新的「为什么」保存在对话里（谁提议、谁反对、为什么上线）。
4. **自举闭环的意识层**：执行可全自动，但「要不要改、改成什么样、什么时候停」需要一个由人与 agent 共同形成的意图。
5. **随处可用**：浏览器/手机/语音都可进，不强制开 IDE。

**但群聊不能是全部。** 必须拆三层，群聊只做「意图/决策层」，避免又当聊天又当数据库。

## 三层架构（与总设计对齐）

| 层 | 承载 | 形态 |
|---|---|---|
| **意图/决策层（群聊负责）** | 讨论、争论、拍板、审批、交接叙事 | 会话 + 决策卡 |
| **结构化状态层（结构化视图负责）** | 版本/Wave、diff、会话重放、审批单、流水线 | 看板/时间线/diff 对比 |
| **执行/观测层（运行时负责）** | 实际运行、写回能力、留痕、回滚 | dsh / 扩展宿主 + 日志/指标 |

**结构性约束**：结构化存储是唯一事实源；群聊是它的叙事入口。对话只放「结论 + 链接」，证据在结构化层。

## 群聊重构要点（设计）

### 1. 对话与决策解耦，但强制关联

- 每次讨论产生意图 → 自动落成一张**决策卡/提案**（关联群聊消息、版本、Wave、改动 diff）。
- 对话是入口和上下文；决策卡才是可审批、可追踪、可回滚的对象；**群聊消息必须能一键跳到对应决策卡**。
- 数据模型建议（P2 落地）：`decision` 表，字段含 `source_message_id / version_id / diff_ref / session_ref / status(proposed|approved|rejected) / decided_by / decided_at / reason`。

### 2. 让「一次拍板」成为闭环内一等动作

- `@架构Agent 讨论` → **@linlis-super-harness（WorkPanel 组完整自举执行者；普通群 @极简 bootstrap-dsh）** 出方案 + dry-run → **在群聊里直接呈现 diff/风险** → 管理员 `@批准` → 走灰度 → promote。
- 整条链从最初消息一路可追溯；审批是群聊原生行为（类似现有 `approve-prod-release.sh` 的群化版）。
- 增加内置动作词（slash 命令），例如：`/propose`（发起提案）、`/approve #决策卡`、`/reject #决策卡`、`/replay #会话`、`/diff #版本`。

### 3. 角色化议事，而不是自由聊天

- 群内职能明确：**决策人（human admin）** / **提案 Agent** / **评审 Agent** / **执行 Agent** / **QA·门禁 Agent**。
- **执行 Agent 固定为两级不可修改的 DSH 预制 Agent**（均 `system_locked` 不可编辑/移除）：
  - **WorkPanel 组 = `linlis-super-harness`**：唯一拥有「面板自举/自改」完整流程执行权。
  - **普通群 = 极简 `bootstrap-dsh`**：仅组内 dsh 执行 + 基础干跑，无自举写回权。
  - 其余普通 Agent 一律无自举写入权限。
- 谁有权提议、谁有权驳回、谁有权批准，写入规则（强化现有群公告 + AGENTS）。
- 权限通过现有 `admin_member_id` + 角色描述表达；审批人必须是人（root 语义延续）。

### 4. 把关口做成不可绕过的护栏

- Agent 不能自我批准、不能伪造批准令牌、不能绕过灰度直接 promote。
- 自举类改动必须带「可回放会话 / 干跑结果」才能进审批；禁止只丢一句「给我权限」。
- 审批动作落 `decision` 表，配套日志（`source=governance`），可审计、可追责。

### 5. 上下文卫生：聊天要「轻」，状态要「重」

- 滚动摘要、pin 决策、按 `@` 聚焦、epitaph 摘要注入（复用 `context_seams` 切片）。
- 一张决策的全部证据（会话重放、运行日志、diff）放结构化层；群聊只放结论与链接。
- 限制单提案上下文预算；过期决策自动归档。

### 6. 给自举频率上纪律

- 群聊 + 版本/Wave 本身就是吞吐闸门：默认灰度、有限并发、冻结窗口、drain。
- 「闲聊群」与「项目群」职责分开：讨论与决策可以在不同群，但决策最终落在版本/Wave 结构化层。

## MVP 边界（P1 之前的起步）

- 先做「决策卡」的最小版：`/propose` 把一条群聊消息升级成可审批对象，审批打 `approved/rejected`，并在版本页显示来源消息。
- 不在本阶段实现会话重放/热载（那是 P1/P2 的事）；群聊治理层先立住「意图→决策→审批」这条线。

## 验收

- 群聊内 `/propose` 可生成决策卡，`/approve`/`/reject` 可改变状态并留痕。
- 版本页可看到每条 Wave 的「来源决策卡 + 审批人 + 理由」。
- 无任何 Agent 路径能绕过 `manually_approved` 直接 promote。
- 灰度回归 + 前端壳冒烟后 promote；全程走现有 test:gate 门禁。
